## 0. このドキュメントの読み方

外部からの観察（HTML取得・スクリーンショット・141秒の画面録画のフレーム解析）に基づく評価をまとめたもの。**実装者は各項目の「確度」を確認してから着手すること。**

| 確度 | 意味 |
|---|---|
| **確定** | 取得したHTML・画像から直接確認できた事実 |
| **要確認** | 外部からは断定できず、実機・ソース確認が必要 |
| **提案** | 事実ではなく設計上の提案 |

評価中に4つの実装済み機能（Relive Player / Creator Relations / 公演ヒートマップ / On This Day）を「未実装」と誤認した。いずれもトップページから辿れないことが原因。**同種の誤りが本ドキュメントにも残っている可能性がある。**

## 2. バグ・データ不整合

### 2-1. サイト内の数字が一致しない【確定】

| 掲載場所 | 数値 |
|---|---|
| TOP | 131 SONGS / **170** LIVES / 2,120 PERFORMANCES |
| TOP内カード | 「**167**公演のセトリアーカイブ」「**130**曲の演奏回数」 |
| `/songs/stats/` | 述べ演奏 **1,851** / ユニーク **114** / 131曲 |
| `/live/` | **76**件 |
| ヒートマップ | 国内133 + 海外17 = 150、不明/未確定 20 |

**推定される整合**（要確認）:
```
133 (国内) + 17 (海外) = 150
150 + 20 (不明/未確定) = 170  ← TOPの「170 LIVES」と一致
```
167 は「不明/未確定」の一部を除外した数と思われる。

**対応**
- 集計ロジックを単一のソースに統一し、全ページの数値をそこから生成
- 「公演数」「イベント数」「述べ演奏数」の定義を確定
- TOPの表記を `170 LIVES（うち20件は日程・会場が未確定）` に変更
- `/about/data/` を新設し、集計ルール（未発表曲/中止公演/SE・インストの計上可否）を明記

## 3. UI / UX 改善

### 3-1. ヒーロー動画のファサード化【提案・優先度高】

**現状の問題**
- 全ページ最上部でファーストビューの約40%を占有
- YouTube埋め込みのタイトルバーが**起動後3秒以上、白い矩形として表示される**（0.2s / 0.8s / 1.4s / 2.0s / 2.6s / 3.2s の全フレームで確認）
- ダークサイトで唯一の白であり、初訪問者が最初に見るものになっている

**対応**
- 自前サムネイル＋再生ボタンを表示し、タップ後に初めて iframe を差し込む（ファサード方式）
- 白帯が消え、初期表示も軽くなる
- PLACEページで既に公式サムネイルを使用しているため実装の型は流用可能
- 配置は HOME のみ、かつヒーロー（コピー＋数字）の**下**へ

---

### 3-2. PiP（縮小追従表示）を再生中のみに【提案】

**実測**: 8s / 12s / 16s / 20s / 30s / 45s / 60s / 75s / 100s / 120s の**全サンプルフレームの右上に表示されていた**。ページ遷移をまたいでも消えず、141秒間ずっと画面に存在。

✕で消せる仕様だが、自然な回遊では消されずに残り続けた。

**対応**
- 動画を能動的に再生している時のみ PiP 化。未再生ならスクロールアウトさせる
- PiP化する場合も幅は画面の30%程度に抑える
- ✕で閉じた状態を `sessionStorage` に記録し、以降のページ遷移でも復活させない

### 3-9. 関連ポスト（X埋め込み）の扱い【重要・方針転換あり】

#### 計測結果：関連ポストは最も読まれているコンテンツ

画面録画から、セクションごとに「静止（読んでいる）」と「スクロール（流している）」の比率を実測。

| 区間 | 静止率 | 最長停止 | 停止回数 |
|---|---|---|---|
| **31–70s 関連ポスト** | **62%** | **5.6秒** | 33回 |
| 0–31s HOME | 34% | 2.7秒 | 25回 |
| 96–141s DISCO・楽曲 | 40% | 0.9秒 | 61回 |

関連ポスト区間はセッション中で唯一「読む」挙動が出ている場所。**当初提案した「3件までに制限」は撤回済み。減らさないこと。**

#### 対応1: セクション順序（短い → 長い）

優先度とは別に、**長いセクションを短いセクションの前に置くと後ろが到達されない**という制約がある。

```
現状（楽曲詳細）              変更後
─────────────────            ─────────────────
メタ情報（短）                メタ情報（短）
関連ポスト（長・没入型）       PERFORMANCE HISTORY（短・一覧型）
PERFORMANCE HISTORY（短）      関連ポスト（長・没入型）
```

PERFORMANCE HISTORY は通過コストがほぼゼロのため、先に置いても関連ポストの体験を損なわない。逆は成立しない。ライブ詳細の OTHER DATES も同様。

#### 対応2: 日付差分の自動ラベル（手入力ゼロ）

既存データ（ポストの日付・公演日/リリース日・アカウント）の差分から機械生成できる。

```
▸ 公演2日前 · 本人
▸ 公演当日 · 公式
▸ 公演翌日 · 本人
▸ リリース3ヶ月前 · 公式
```

これだけで「なぜこのポストがここにあるか」がほぼ伝わる。**費用対効果が最も高い施策。**

#### 対応3: 固定タグ（1クリック）

自由記述ではなく選択式にすることで運用コストを抑え、同時にフィルタ軸としても使う。

```
告知 / 制作背景 / ライブ後の所感 / 衣装・ビジュアル
裏話 / 共演者言及 / メディア掲載 / ファン向け
```

#### 対応4: 任意の注釈（無理をしない）

- **遡らない** — 既存分は放置し、今後追加分にのみ任意で付与
- **ページごとに1件だけ** — 先頭1件に注釈があればセクション全体が「編集されている」ように読まれる
- 任意フィールドとし、注釈が無くても成立する設計にする

#### 対応5: 可用性リスクへの備え

X埋め込みはX側のスクリプトに依存し、仕様変更・レート制限・アカウント削除で消える。アーカイブサイトとして構造的な弱点。

**ただしポスト本文を自前でレンダリングし直すのはXの表示要件と衝突しうるため非推奨。**

現実的な折衷:
- 表示は公式埋め込みのまま
- 投稿日・URL・自サイトの注釈は自前データとして保持
- 埋め込み失敗時は「注釈＋日付＋リンク」にフォールバック

### 3-10. On This Day の改善【優先度高】

#### 空になる日への対策（最重要）

イベント総数はリリース＋公演で概算400件前後、対して365日。ツアーは春、フェスは夏に集中するため、**実際には年の半分近くが空になる。**トップに置く要素が半分の日に空になるのは機能として成立しない。

**段階フォールバックを実装すること**
```
1. 今日ちょうど   → 「14年前の今日」
2. ±3日以内      → 「3日前の今日」「明後日で◯周年」
3. 同月内         → 「今月の出来事」
4. 直近の未来     → 「次の記念日まであと5日」
```
4まで用意すれば絶対に空にならない。「あと5日」は再訪の動機になるため、空だった日の方が強いコンテンツになりうる。

#### リンクを張る

『magician's operation』も MINGLE も対応するページが存在するはず。**現状リンクがない。**繋ぐだけで毎日変わる内部リンクがトップに生まれる。

#### 日付ごとの固定URLを生成

```
/on-this-day/07-26/  ... 365ページ静的生成
```
- 自分の誕生日を調べる遊びが成立
- 365ページ分の実データを持つインデックス面が増える
- 「7月26日 Reol」等の検索に対応
- **DBにフィルタを掛けるだけで新規データはゼロ**

#### 配置

現状トップから辿れない位置にある（HTMLにも141秒の回遊にも出現しなかった）。`NEXT LIVE` の隣へ移動する。

```
NEXT LIVE:   07.26 Zepp New Taipei                  ← 今日から見た未来
ON THIS DAY: 14年前の今日『magician's operation』    ← 今日から見た過去
```

現状のファーストビューは 131 / 170 / 2,120 という**変わらない数字**のみ。毎日変わる要素を並べることで「今日来た価値」が生まれる。

#### 自動投稿

ビルド時にその日の1件をテキスト化してスケジュール投稿すれば、運用コストゼロで毎日1回の露出が生まれる。**機能そのものよりこちらが本体。**

### 3-11. Relive Player の改善【提案】

対象はマニア向け機能であり、期待値を上げる方向の変更はしない。

#### 期待値の事前調整
- ラベルを `Relive Player (β) ― 要・自前音源` に変更し、条件を文言に含める
- ボタンを枠線グレーのセカンダリに落とし、会場リンクと並列以下の扱いに

#### 失敗状態を前面に出す

**現状**: `matched 0 / candidate 0 / missing 24 / special 1` が折りたたみの中、かつプレイヤー本体より下にある。「なぜ再生できないのか」が再生ボタンを押した後にしか分からない。

**対応**
- フォルダ選択直後に結果を表示（`24曲中 0曲が一致しました`）
- 未一致の曲名をリスト表示し、期待するファイル名の形式を提示（例 `01_第六感.m4a` / `第六感.mp3`）
- 曲名 → ファイルの手動ひも付けUI
- 一致0件の間はプレイヤー部分を淡色または非表示に（現状 `1/1` `0:00 / 0:00` `(Remix)` と表示され、初見では壊れて見える）

#### その他
- **Wake Lock はデフォルトON推奨**（25曲通し再生中に画面消灯で停止しかねない）。Media Session も同様
- Chrome/Android は File System Access API のハンドルを IndexedDB に保存し、次回以降の再読み込みをスキップ可能（iOS Safari 非対応）
- 「公演記憶を保存」が何を保存するのか読み取れない。ヘルプまたは短い説明を追加
- 推定PA構成の但し書きは良い。将来的に `⚠推定` / `✓実測` のバッジ化で情報提供の導線にできる
- EQ・リバーブに「ホール」「Zepp」「フェス野外」等のプリセット入口を追加

## 4. 構造・SEO

### 4-1. `/features/` の新設【最優先】

全機能を1行説明付きで列挙するページ。深層機能（Relive Player / Creator Relations / ヒートマップ / On This Day）が**トップからも検索からも辿れない**ことが、評価中に4回の見落としを生んだ根本原因。

運営者自身の管理台帳としても機能する。

### 4-2. `/lab/`（DEEP DIVE）の新設【提案】

深層機能を集約するハブ。

- ヒートマップ / 楽曲統計 / Creator Relations / Relive Player(β) / On This Day
- 各機能に1〜2行の説明と難易度ラベル（`だれでも` / `要・自前音源`）
- トップの EXPLORE に1枠「LAB ― もっと深く掘る」を追加

**ただしヒートマップは LAB ではなく LIVE 配下の正規メニューへ。**

### 4-3. 統計テーブルから楽曲ページへの直リンク【確定・優先度高】

`/songs/[slug]/` は既に静的生成されているが、`/songs/stats/` からの導線が `?songSlug=` 経由になっている（要確認）。

**対応**: 統計テーブルの各行を `/songs/[slug]/` に直リンク。これだけで内部リンクが数百本増える。

### 4-4. 構造化データ

- 楽曲ページに `MusicRecording`
- 公演ページに `MusicEvent`

### 4-5. ページ別OG画像の自動生成【提案】

現状 OG画像が全ページ共通（`/ogimage.png`）。ビルド時に satori 系でページ固有の画像を生成する。

```
第六感
演奏88回 · 初披露 2020-08-16
```

**既存データを画像化するだけで新規執筆はゼロ。**

### 4-6. PWA化＋オフラインキャッシュ【提案】

既にタブバーでアプリの体裁をとっており、`apple-mobile-web-app-capable` も設定済み。

**会場は電波が死ぬ。**開催中ツアーのセトリと会場情報を事前キャッシュしておけば「現地で開けない」を回避できる。ライブ用サイトとしての実用性が一段上がる。

### 4-7. データセットの公開【提案】

セトリ・楽曲・公演データを JSON / CSV で配布。「二次利用可・出典明記」で公開すれば、研究者・他ファン・setlist.fm系サービスから参照され、被リンクと権威性が生まれる。

### 案F: 楽曲ソーター
**元ネタ**: キャラソート（マージソート式）× Spotify Wrapped

131曲を2曲ずつ提示し、好きな方を選び続ける。約200回の比較で全131曲の個人ランキングとシェア画像が完成。

**この案の本質は遊びではなく、サイトに欠けているデータの取得。**

現在あるのは「Reolが何回演奏したか」という客観データのみ。ここに「ファンがどれだけ好きか」という主観データが加わると新しい軸が生まれる。

```
演奏回数 × ファン人気度の散布図

  右上：定番曲
  左上：ファン人気は高いが、ほとんど演奏されない曲  ← 「生で聴きたい曲」
  右下：よく演奏されるが、投票では上位に来ない曲
```

**左上の象限はそれ自体がコンテンツ。**「ファンが最も生で聴きたい封印曲ランキング」は他所には出せない。一度回してもらえば、以降は集計更新だけで毎年コンテンツになる。

### 案H: セトリの「文法」解析
**元ネタ**: The Pudding（データビジュアルエッセイ）

- **ツアー内の変化** — 初日と最終日で何が入れ替わったか

現在の統計ページが「辞書」なら、これは「文法書」。セトリ予想の根拠にもなり、参戦中にリアルタイムで使える知識になる。

## 6. 検討したが見送るもの（再提案しないこと）

| 項目 | 理由 |
|---|---|
| Relive Player をトップの目玉に格上げ | 自前音源が必要でハードルが高い。マニア向けとして維持する方針 |

| 歌詞の語彙年表 | 出力（統計値）は成立しうるが、解析元データの入手方法に慎重さが必要。条件付き保留 |
| Spotify Audio Features を使った楽曲分析 | 2024年11月に新規アプリ向けが提供終了。依存しない |
| ユーザー投稿型の参戦レポ | モデレーション負荷が高い。X検索リンク集で代替する方が現実的 |

## 9. 実装時の注意
