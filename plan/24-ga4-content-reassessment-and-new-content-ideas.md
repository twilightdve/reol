## 0. GA4再認証の経緯(解決済み)

作業開始時点で`analytics-mcp`のOAuthトークンが失効(`invalid_grant`)しており、ユーザーに以下のコマンドで再認証を依頼した。

```bash
gcloud auth application-default login \
  --client-id-file="$HOME/.config/reol-ga-mcp/client_secret.json" \
  --scopes=https://www.googleapis.com/auth/analytics.readonly,https://www.googleapis.com/auth/cloud-platform
```

初回は`--scopes`に`cloud-platform`が必須というエラーで失敗、2回目のコマンドで認証成功。ただしMCPサーバープロセスがセッション起動時の古いトークンをメモリ上に保持したままだったため、その後もツール呼び出しは`invalid_grant`のままだった。**セッションを再起動(resume)した後に再度試すと正常に動作した**([[mcp-server-needs-restart]]と同種の問題)。

### 1-7. 新たに見つかったエラーイベント: `data_load_error`(原因特定済み)

直近28日で`data_load_error`イベントが3件発生しており、すべて`/quiz/reol-type/`ページで発生している。コードを確認したところ、`src/pages/quiz/reol-type/index.tsx`が診断結果ページ上部の「タイプ分布」表示のためにSupabase(`profiles`テーブルの`reol_type`集計)を取得しており、この取得が失敗した場合に`trackEvent('data_load_error', { category: 'data', label: 'reol_type_distribution' })`を発火する実装になっていた。

つまり原因は**サイトのコードバグではなくSupabase側の取得失敗(タイムアウト等)**で、失敗時は分布マトリクス自体を非表示にするフォールバックがある(`supabase`未設定時と同じ扱い)。件数(3件/28日)は全体からすれば小さいが、**サイト最大の集客ページで外部サービス依存の失敗が一定確率で起きている**ことは事実であり、頻度が増えるようなら再試行(リトライ)やタイムアウト値の見直しを検討する価値がある。同種の`data_load_error`は他に`SetlistPrediction.tsx`(2箇所)・`PlaceSection.tsx`(place_map)・`SafeTweets.tsx`(twitter_widget)・`song-live-history.tsx`(未使用コードのため実質発火しない)でも計装済み。

## 2. コンテンツ評価: コード実査で見つかった具体的なギャップ

現在のページ構成・データモデルを棚卸しし、「データはあるのに使われていない」箇所を中心に確認した。

### 2-1. 曲詳細ページにSpotify音響特性(Audio Features)が一切表示されていない

`src/types/discography.ts`の`SongFeature`型には、`danceability`・`energy`・`valence`・`tempo`・`key`・`mode`・`loudness`・`speechiness`・`acousticness`・`liveness`・`timeSignature`など、Spotify Web APIから取得済みの音響特性が揃っている。これを**レーダーチャート+数値表示するReactコンポーネントは既に実装済み**(`src/components/index/discography/item-song.tsx`、`recharts`使用、開発コスト込みで323行)だが、このコンポーネントは**現在どこからも呼ばれていないデッドコード**である。

- 呼び出し元の`src/components/index/discography/timeline-item.tsx`(234行)自体も、現在使われている`discography.tsx`→`enhanced-timeline-item.tsx`のチェーンには組み込まれておらず未使用
- 同様に`src/components/index/live/timeline-item.tsx`(285行)も未使用(現行は`live.tsx`→`live/enhanced-timeline-item.tsx`)
- 実際の楽曲詳細ページ`src/templates/song.tsx`(518行)には`feature`関連の描画が一切ない(grep該当ゼロ)

**機会損失**: 楽曲ごとの「キー/BPM/テンポ感」はファンにとって明確な付加価値情報であり、データもコンポーネントも既にあるのに未接続なだけ。§3-1で新規コンテンツとして提案する。

**追記(ユーザー確認事項への回答)**: 「Spotify音響特性取得APIが復活していないか」を確認するようご依頼があったため、Web検索で確認した。結論: **復活していない**。Spotifyは2024年11月27日付でAudio Features/Audio Analysis等のエンドポイントを新規・未拡張枠アプリから恒久的に廃止しており(参照: [Introducing some changes to our Web API](https://developer.spotify.com/blog/2024-11-27-changes-to-the-web-api))、2026年時点の開発者コミュニティでも「復活の予定なし」という報告が確認できる(参照: [Spotify's audio_features API died in 2024. Here's what to use in 2026.](https://dev.to/birrings/spotifys-audiofeatures-api-died-in-2024-heres-what-i-built-to-replace-it-3dn3))。例外は「2024-11-27より前に拡張クォータを取得済みのアプリ」のみで、そのようなアプリは引き続きアクセスできる可能性があるが、これは本サイトのSpotify Developer Dashboard側の設定を直接確認しないと分からない(このリポジトリ内にAPIを叩く取得スクリプトは存在せず、`song_feature`という別シートに値が事前投入されている前提でこのアプリは読むだけの構成)。

### 2-2. LIVE詳細ページの「曲ごとのYouTube映像」が、曲詳細ページの演奏履歴に反映されていない — ✅解消済み(2026-07-30、§3-2参照)

本セッションで`live_item_song`シートの曲別YouTube動画IDをLIVE詳細ページ(`/live/<slug>/`)のセットリストに実装したが、`src/templates/song.tsx`の`Play`型(演奏履歴、PERFORMANCE HISTORYセクション)には`youtubeVideoId`が含まれていなかった。§3-2で`Play`型に追加し、演奏履歴からその場でYouTube映像を視聴できるようにした。

### 2-3. 3種類のコレクション記録(所有/参戦/訪問)が横断集計されていない

`useCollectionOwned`フックがDISCOGRAPHY(`owned`)・LIVE(`attended`)・PLACE(`visited`)の3箇所でそれぞれ独立してlocalStorageに記録されており、各セクション内で「◯/94・◯%」のように個別表示されている。しかし、この3つを横断して「あなたはCD 42枚中◯枚所有、ライブ◯回参戦、聖地◯箇所訪問」とまとめて見せる画面・シェア機能は存在しない。

一方、`bijigaku-navi`側には`src/components/reolmap/layout/ShareButton.tsx`として「選択データをCanvas描画→画像保存/テキストコピー」のシェアカード機能が既に実装済みで、このパターンは流用可能。

### 2-4. 診断クイズ(最大の集客源)で取得したファンタイプが、クイズ以外で一切再利用されていない

`/quiz/reol-type/quiz/`は前回GA4分析で全PVの36%を占める最大の入口だった。診断結果(`reol_type_result`)と簡易プロフィール(`reol_user_profile`)は`localStorage`に保存されるが、参照しているのは`src/contexts/AuthContext.tsx`と診断ページ自身のみで、HOMEや楽曲詳細など他ページでの再利用(「あなたは○○タイプなので、この曲もおすすめ」等のパーソナライズ)は一切実装されていない。

**GA4前回分析の「新規ユーザー比率96.6%」問題と直結**: 診断結果を再訪時に活用する導線が無いため、再訪の動機付けが弱い。

## 3. 新規コンテンツ提案(現在のデータ資産から作れるもの)

優先順位は「データ・コンポーネントが既にある(実装コスト小)」→「新規データ集計が必要(実装コスト中)」の順。

### 3-1. 楽曲の音響特性レーダーチャートを曲詳細ページに復活させる(実装コスト: 中、ただし新譜は恒久的に欠損する前提)

**追記(2026-07-30)**: §4のデッドコード削除(2-2/3-2/4の実装依頼)を先に実施し、この節が前提としていた`item-song.tsx`は**HEADから削除済み**(git履歴には残っている)。以下の記述は執筆時点(削除前)のものなので、実装コスト見積もりを「小」から「中」に修正した。実際に着手する際は`git log`でこのコミット以前の`item-song.tsx`を復元するか、レーダーチャート部分を新規に書き起こす前提で見積もること。「コンポーネントは既に実装済みなので繋ぐだけ」という前提はもう成立しない。

§2-1の通り、データ・チャートコンポーネント(`item-song.tsx`、削除前時点)は既に存在した。レーダーチャートの実装先は楽曲詳細ページ(`/songs/<slug>/`)であり、これは`songStats`(名寄せ済みの代表曲、128曲)にしか存在しないため、`static/data/discography.json`の全251曲(ライブ映像作品の副次収録による重複を含む生データ)ではなく、開発中のGatsby GraphQL(`songStats { songStats { songUuid slug songName } }`)から実際に128件の代表曲リストを取得し、`song_feature`側のカバレッジを突き合わせて再集計した。結果、**代表曲128曲中98曲(約76.6%)にはデータがあるが、直近リリース(2025年11月以降、COCOON/美辞学/オオエドランヴ等)は軒並み欠損している**(下表)。「劣等上等」「うつくしじごく」「美辞目録」など知名度の高い曲も欠損側に入っている。

| リリース日 | タイトル | 特性データ |
|---|---|---|
| 2026-07-11 | COCOON | ✗ 欠損 |
| 2026-01-21 | 美辞学 (Rhetoric) | ✗ 欠損 |
| 2025-11-09 | オオエドランヴ -十年物 Edition- | ✗ 欠損 |
| 2025-08-27 | No title' in NIPPON BUDOKAN(Live) | ✗ 欠損 |
| 2025-01-15 | Reol Oneman Live 'No title' in NIPPON BUDOKAN(Live) | ✓ あり |

**この欠損は「取得し忘れ」ではなく恒久的なもの**: Spotifyは2024-11-27付でAudio Features等のエンドポイントを新規/未拡張枠アプリから廃止しており、2026年時点でも復活のアナウンスは確認できない(詳細は§2-1追記を参照)。したがって新譜(2025年11月以降)のデータは**今後も基本的に取得できない**という前提で実装方針を決める必要がある。

- このリポジトリ内にはSpotify APIを叩く取得スクリプトが存在せず、`song_feature`という別シート(`SpreadsheetService.getSongFeature()`)に値が事前投入されている前提で読むだけの構成。**そのシートを更新している外部プロセス/スクリプトの所在をユーザー側で把握しているか要確認**(拡張クォータ取得済みの個人アプリが今も動いているなら継続利用は可能かもしれないが、これはSpotify Developer Dashboard側の設定を直接見ないと判断できない)
- 実装するなら「新譜には出ない」ことを前提にし、データが無い曲では該当セクションを丸ごと非表示にする(既存コンポーネントは`song.feature`がnullなら個別項目を出し分けている実装なので流用可能)
- データ欠損のまま「看板コンテンツが空に見える」状態で公開すると、plan/21で指摘された`/songs/stats/`と同種の失敗を繰り返すため要注意。特に**直近リリースほどSNSでの言及・アクセスが集中しやすく**(§1-3の`/songs/cocoon/`直接着地4セッション等)、その最新曲でこそ空欄になるという点は運用上の弱点になりうる

実装するなら`song.tsx`の該当セクション(現状「②演奏統計カード」付近が自然)にレーダーチャートを追加する形になる。新規のAPI呼び出しは不要(既存の`song.feature`をGraphQLクエリに追加するだけ)だが、チャート描画コンポーネント自体は上記の通り書き起こしが必要。

### 3-2. 演奏履歴(PERFORMANCE HISTORY)に「映像あり」バッジを追加 — ✅実装済み(2026-07-30)
