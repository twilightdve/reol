# 3. UI/UX改善提案(優先度順)

優先度の定義:

- **P0**: すぐ直すべき不具合・機会損失
- **P1**: 人気向上・回遊性向上に直結する重要改善
- **P2**: 体験を豊かにする改善
- **P3**: 将来的に検討する改善

---

## P0-1: SEOデフォルトdescriptionがツアー文言のまま

- **現状の問題**: `src/components/SEO.tsx:11` の `DEFAULT_DESCRIPTION = '美辞学ツアーの会場情報や参加者をチェックできます'`。descriptionを渡さないページ全てで、内容と無関係なツアー文言が検索結果・SNSカードに出る
- **ユーザーへの影響**: 検索結果でのCTR低下、SNS共有時の誤解
- **改善内容**: デフォルトを「Reolの楽曲・ライブ・セトリ・聖地を横断できる非公式ファンサイト」系の汎用文に変更し、全ページで明示的にdescriptionを渡す監査を実施
- **実装イメージ**: SEO.tsx 1行変更+各ページのHead監査(grepで `<SEO` 呼び出し箇所を列挙)
- **期待効果**: 検索CTR改善、共有時の信頼感
- **実装コスト**: 小(1〜2時間) / **リスク**: なし
- **成功指標**: Search ConsoleのCTR
- → [Issue 1](./issues/issue-01-seo-default-description.md)

## P0-2: トップのmeta descriptionが謝罪文

- **現状の問題**: `gatsby-config.ts:10-11` の siteMetadata.description が「自己満足的な…間違いなどあるかもしれませんが」。これがトップのdescription・og:description・twitter:descriptionすべてに出ている(実HTMLで確認済み)
- **ユーザーへの影響**: 検索結果とXカードで初見の人を弾く。サイト最大の入口が最弱の文章
- **改善内容**: 謙遜はABOUTに残し、metaは価値提案に([04-copywriting.md](./04-copywriting.md) 参照)
- **実装コスト**: 極小(15分) / **リスク**: なし
- **成功指標**: 検索CTR、X経由流入
- → [Issue 2](./issues/issue-02-top-meta-description.md)

## P0-3: データページが「読み込み中…」のまま(初期HTML空+エラー時無反応)

- **現状の問題**: `/songs/stats`、`/search`、`/bijigaku-navi/setlist-prediction` は初期HTMLにデータがなく「読み込み中…」表示(実確認済み)。検索ページはタブが「すべて(0) 楽曲(0)…」と0件表示。フェッチ失敗時のエラーUIは未確認(推測: なし)
- **ユーザーへの影響**: SEO上は空ページ。低速回線・失敗時は「壊れたサイト」に見える。検索の(0)は「データがないサイト」という第一印象を与える
- **改善内容**:
  1. ビルド時にデータを静的生成へ寄せる(演奏統計はビルド時計算可能なはず)。少なくとも総曲数・上位曲などのサマリを初期HTMLに含める(※本サイトはGitHub PagesホストのSSGでSSRは不可)
  2. ローディングをスケルトンUIに
  3. 件数はロード完了まで非表示
  4. 失敗時は再試行ボタン付きエラー表示
- **実装コスト**: 中(2〜5日) / **リスク**: ビルド時間増、データ更新頻度との兼ね合い
- **成功指標**: statsページの直帰率・検索流入
- → [Issue 4](./issues/issue-04-stats-ssr.md), [Issue 9](./issues/issue-09-search-empty-state.md), [Issue 13](./issues/issue-13-loading-error-states.md)

## P0-4: `<html lang>` 欠落・JSON-LDなし

- **現状の問題**: 実HTMLで `<html><head>` に lang属性なしを確認。構造化データも全サイトでゼロ(grep確認済み)
- **ユーザーへの影響**: アクセシビリティ(スクリーンリーダーの言語判定)、SEO(言語判定・リッチリザルト機会損失)
- **改善内容**: `gatsby-ssr.tsx` に `onRenderBody` で `setHtmlAttributes({ lang: "ja" })`。JSON-LDは [06-seo-sns.md](./06-seo-sns.md) 参照
- **実装コスト**: langは10分、JSON-LDは1〜2日 / **リスク**: なし
- **成功指標**: リッチリザルト表示、Lighthouseスコア
- → [Issue 3](./issues/issue-03-html-lang.md), [Issue 10](./issues/issue-10-json-ld.md)

## P0-5: 公式送客ハブの不在

- **現状の問題**: 公式リンクは reol.jp がABOUTダイアログ内に1つだけ。公式YouTube・公式X・Instagram・配信(Spotify/Apple Music等の公式リンクページ)・チケット導線がサイト内に常設されていない
- **ユーザーへの影響**: 「もっと聴きたい」と思った瞬間の受け皿がなく、最重要方針(公式送客)が構造的に果たせていない
- **改善内容**: フッターを全ページ共通で「OFFICIAL LINKS」ブロック化(公式サイト/YouTube/X/Instagram/配信/チケット)。トップと楽曲・ライブ詳細にも文脈的CTAを配置
- **実装イメージ**: `src/components/modules/` に OfficialLinks コンポーネント新設、body.tsx またはフッターに組み込み
- **実装コスト**: 小(半日) / **リスク**: リンク先の変更追従のみ
- **成功指標**: 公式リンククリック率(GA4イベント)
- → [Issue 5](./issues/issue-05-official-links-footer.md)

## P1-1: ファーストビューに「サイトの価値」と新規向け導線がない

- **現状の問題**: トップはオープニング演出→公式MV埋め込み→診断/美辞学ナビバナー→Pick Up Post。サイト名「!Legit」の意味も、何ができるサイトかも、ABOUTダイアログを開かないと分からない
- **ユーザーへの影響**: 新規の直帰。SNS流入した非ファンを取りこぼす
- **改善内容**: MV下に1〜2行のタグライン+3枚の入口カード(「はじめてのReol」「ライブに行く」「深く掘る」)を常設。ABOUT要約もインライン表示
- **実装コスト**: 小〜中(1〜2日) / **リスク**: 既存ファンには冗長→スクロールで流せる軽さにする
- **成功指標**: トップ→下層遷移率、直帰率
- → [Issue 7](./issues/issue-07-top-entry-cards.md)

## P1-2: ページタイトルのサイト名表記ゆれ

- **現状の問題**: 「検索 | Reol Fan Site」「楽曲統計 | Reol Fan Site」「LIVE | !Legit｜Reol Unofficial Fansite」「美辞学ナビ - 会場・アクセス・参加者情報」「あなたはどのReolタイプ？ — 16タイプ診断」と最低4系統(実確認済み)
- **ユーザーへの影響**: 検索結果でのブランド認知が分散。「Reol ファンサイト」等の指名検索評価も分散
- **改善内容**: `ページ名 | !Legit - Reol非公式ファンサイト` に統一。SEO.tsxでサフィックスを一元管理し、ページ側はページ名だけ渡す
- **実装コスト**: 小(半日) / **リスク**: なし
- **成功指標**: 指名検索インプレッション
- → [Issue 6](./issues/issue-06-title-unification.md)

## P1-3: 「美辞学ナビ」の一般化(ツアー終了後の鮮度切れ対策)

- **現状の問題**: ヘッダー一等地の「美辞学ﾅﾋﾞ」(半角カナ)はツアー固有名。新規には意味不明、ツアー後は古く見える。タイトルも「会場・アクセス・参加者情報」とツアー文脈のみ
- **改善内容**: 機能を「ツアーナビ」(常設機構)+「美辞学アーカイブ」(ツアー資産の保存)に再編。次ツアー発表時に即座に次期ナビへ転用できる構造にする。ヘッダー表記は現ツアー名 or 「LIVEナビ」
- **実装コスト**: 中(3〜5日、命名とルーティング整理) / **リスク**: 既存URL変更はリダイレクト必須
- **成功指標**: ナビクリック率
- **推測注記**: 美辞学ツアーの会期状況は未確認。会期中なら本件はP2に落とし、終了確定後に実施

## P1-4: 楽曲統計→曲詳細→公式動画の連鎖が切れている

- **現状の問題**: statsは一覧表で終点。曲名から「その曲のセトリ登場ライブ」「公式MV」へ飛べない(一覧ページの実表示から判断。詳細実装は推測込み)
- **改善内容**: 曲ごとの詳細ビュー(演奏履歴タイムライン・初出/最終・公式MVリンク)を用意し、stats・検索・セトリから全て曲詳細に集約
- **実装コスト**: 中〜大(1〜2週) / **リスク**: データ整合性
- **成功指標**: stats→曲詳細遷移率、公式動画クリック

## P1-5: 診断結果のOGPがタイプ別になっていない

- **現状の問題**: 共有カード画像生成+X intent+navigator.shareは実装済み(`result.tsx`, `reol-type-detail.tsx` で確認)だが、og:imageは全サイト共通の ogimage.png。共有URLを踏んだ人にはタイプが見えない(タイプ別ページのog:image上書き有無は未確認・推測)
- **改善内容**: 16タイプ分の静的OG画像を生成し、タイプ別ページのHeadで `image` を渡す。共有はこのURLに誘導
- **実装コスト**: 小〜中(1〜2日) / **リスク**: なし
- **成功指標**: 診断共有率、共有URL経由の新規セッション
- → [Issue 8](./issues/issue-08-quiz-type-ogp.md)

## P2-1: モバイルヘッダーがアイコンのみ

- **現状の問題**: 検索・楽曲統計はモバイルで `hidden sm:inline` によりアイコンだけ(`header.tsx:50-61`)。楽曲統計のグラフアイコンは初見で意味が取れない
- **改善内容**: モバイルは下部固定タブバー(ホーム/検索/LIVE/もっと)化、またはラベル常時表示
- **実装コスト**: 中 / **リスク**: 画面占有
- **成功指標**: モバイルのナビ利用率
