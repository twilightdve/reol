# 76. サイトの評価方法の調査(チェッカースキルの下調べ)

2026-11-17。ユーザーから。

- 「現状のサイトのパフォーマンスやアクセシビリティ、サイトデザインの質、コンテンツの内容を評価するチェッカースキルを作りたい」
- 「まずは現状の評価をレポーティングしてほしいが、どのような評価方法があるか調査するところから始めて」

この文書は「どんな評価方法があるか」と「このサイトにはどれが合うか」。実際に測った結果は [plan/77](./77-site-evaluation-2026-11.md)。スキル本体はまだ作っていない。

書き分け: **確認**=このセッションで実際に動かして確かめた / **参考**=出典に書いてあること / **未確認** / **推測**。

## 1. 先に結論

- 4 つの領域とも「機械で測れる部分」と「人が見ないと決まらない部分」がある。機械だけで点を付けると、測れる部分しか見ていない点になる。スキルは **機械の測定 → 見る人(Claude)の判断 → 人にしか確かめられない残り** の 3 段で報告するのがよい。
- 道具は足りている。Lighthouse(速さ)、axe-core(アクセシビリティ)、Playwright で書いた自前の調べ(キーボード・見た目の数え上げ・画面写真)、ビルド済み HTML の総なめ(コンテンツ・メタ情報)。どれもこの PC で動いた(確認)。
- 速さは **本番** で測る。それ以外は **ローカルのビルド** で測る。ローカルの速さの点は本番と比べられない(確認)。
- 道具の結果をそのまま信じると間違う箇所が 1 つあった。このサイトは `html` と `body` に背景色が無く、色は固定の層が塗っている。道具は背景を白と見なすので、暗いテーマの文字色を全部「コントラスト不足」と数える(確認。7,284 件の誤検出)。スキルには、測る前に本当の背景色を入れる手当てが要る。
- 実際の利用者の数字(フィールドデータ)は今回取れていない。PageSpeed Insights の API は鍵なしだと 429 で断られ、GA4 の連携は接続に失敗した。

## 2. 領域ごとの評価方法

### 2-1. パフォーマンス

| 方法 | 分かること | 限界 | 試したか |
|------|-----------|------|---------|
| **Lighthouse**(13.6.0) | 点(0〜100)、FCP・LCP・TBT・CLS・Speed Index、重いファイル、遅い原因の候補 | 実験室の値。1 回ごとにぶれる。同時に走らせない | 試した。本番 12 ページ |
| Core Web Vitals のフィールドデータ(CrUX、PageSpeed Insights、Search Console) | 実際の利用者の LCP・INP・CLS(75 パーセンタイル) | 利用が少ないサイトはデータが出ない。PSI の API は鍵が要る | 取れなかった |
| Lighthouse CI | 決めた URL を毎回測り、予算を超えたら落とす | 用意に手間。今は不要 | 試していない |
| Unlighthouse(0.19.1) | サイト全体を自動でたどって全ページ測る | 2,800 ページは重すぎる。この PC では向かない | 試していない |
| 自前の Playwright 計測(`PerformanceObserver`) | どの要素がいつ何 px ずれたか | 自分で書く必要がある | 試した。ずれの原因を突き止めるのに使えた |

参考(出典 1〜5):

- Lighthouse の点の重み(13 系): TBT 30%、LCP 25%、CLS 25%、FCP 10%、Speed Index 10%。0〜49 が赤、50〜89 が橙、90〜100 が緑。
- ぶれの扱い: 5 回の中央値にするとぶれは約半分。同時に走らせない。ローカルの資源が足りない時は、外の測定環境を使う。
- Core Web Vitals の「良い」の線: LCP 2.5 秒以下、INP 200ms 以下、CLS 0.1 以下(75 パーセンタイル)。INP は実際の操作が無いと測れないので、実験室では TBT が代わり。
- CrUX に載るのは、公開されていて、十分に使われているページだけ。

確認:

- 本番と同じビルドをローカルで配って HOME を測ると、点は 63 だった(本番の HOME は 81)。ローカルは圧縮やキャッシュの出方が違う。**速さは本番で測る**。
- スマホ想定は 3 回の中央値にした。同じページでも点が 71〜81、83〜100 と動いた。1 回だけの値で判断しない。
- このサイトは自動操作のブラウザで GA を送らない作り(plan/58)なので、Lighthouse を本番に何度当ててもアクセス数は汚れない(48 回の計測で `collect` の送信は 0)。
- Lighthouse の CLS は、読み込み直後の「操作の直後」扱いのずれも数に入れる。自前の計測でそれを捨てると同じずれが見えなくなる。両方出すと原因にたどり着けた(plan/77 の 2-2)。

### 2-2. アクセシビリティ

| 方法 | 分かること | 限界 | 試したか |
|------|-----------|------|---------|
| **axe-core**(4.14.1)を Playwright で当てる | WCAG 2.0〜2.2 の A・AA と、望ましい作法の違反。要素ごとに場所が出る | 機械で分かるのは一部。「要確認」が大量に出る | 試した。38 ページ × 2 幅 × 2 テーマ |
| Lighthouse の accessibility の点 | axe の一部を重み付きで点にしたもの | 点が高くても問題なしではない | 試した |
| pa11y(10.0.0)、html-validate(11.21.1) | 別の検査器での見直し、HTML の文法 | axe と重なる | 試していない |
| **キーボードで歩く**(Tab を順に押して記録) | フォーカスの順番、印が見えるか、固定の帯に隠れないか、本文まで何回かかるか | 自前で書く。意味の正しさは人が見る | 試した。10 ページ |
| 自前の調べ | 押せる物の大きさ、スキップリンク、見出しの段飛ばし、`lang`、横はみ出し、本当の背景でのコントラスト | 同上 | 試した |
| 読み上げ(VoiceOver など)、実機 | 実際に使えるか | 人がやる | やっていない |
| WCAG-EM、JIS X 8341-3 の試験 | 「適合」を言うための正式な手順 | 重い。ファンサイトには過剰 | ページの選び方だけ借りた |

参考(出典 6〜12):

- axe-core が見つけるのは、件数で見て問題の約 57%(Deque の報告)。基準の数で見ると、WCAG 2.1 AA の 50 の達成基準のうち機械で判定できるのは 16 という報告もある。**機械で 0 件でも適合とは言えない**。
- axe-core は「間違って違反と言わない」方針で、判断できないものは「要確認(incomplete)」に回す。
- WCAG 2.2 で増えた基準: 2.4.11 フォーカスが隠れない、2.5.7 ドラッグ操作、2.5.8 押せる物の大きさ(24×24px 以上)、3.2.6、3.3.7、3.3.8。4.1.1 は削除。
- ページの選び方(WCAG-EM、JIS の試験の手引き): 役割の違うページを意図して選んだものと、無作為に選んだものを足す。100 ページを超えるサイトなら 40〜50 ページが目安。

確認:

- 選んだのは 38 ページ(意図して選んだ 34 と、種を固定した無作為の 4)。スマホ幅 390×844 と PC 幅 1280×800、暗いテーマと明るいテーマで 152 画面。
- **白い背景の誤検出**。`html` と `body` の背景が透明で、色は `fixed` の層(`body.tsx`)が塗っている。axe、Lighthouse、Impeccable は背景を白と見なし、暗いテーマでは `color-contrast` が 36 ページ・7,284 件出た。本当の背景色を `html` に入れてから測り直すと、違反が残ったのは 4 ページだけだった。
- 手当ての副作用もあった。独自の明るい背景を持つページ(`/bijigaku-navi/`)では、入れた背景色のせいで逆に間違った違反が出る。こういうページは別に扱う。
- スキップリンク、本文までの Tab の回数、固定の下部タブに隠れるフォーカスは、axe では出ない。キーボードで歩く調べで初めて分かった。

### 2-3. デザインの質

デザインには決まった点数の出し方が無い。使える物差しは 3 種類。

| 方法 | 分かること | 限界 | 試したか |
|------|-----------|------|---------|
| **このサイト自身の基準に照らす**(plan/71 のカードを減らす方針、黒×公式青×黄の使い分け、unslop の磨き方) | 決めたルールからのずれ。数えられる: 11px 未満の文字、枠つきの箱、絵文字、グラデーション、`transition: all`、4px 刻みでない余白、文字サイズの種類、トークンに無い色 | 「ルールどおり」と「良い」は別 | 試した。自前の調べ、38 ページ |
| **画面写真を並べて見る** | 画面ごとの揃い方、古い見た目の残り、状態の表示の間違い | 見る人の判断。再現性は低い | 試した。76 枚 |
| Impeccable(4.9.2)の `detect` | 62 の決まった規則での引っかかり(小さすぎる文字、光る飾り、見出しの上の小ラベルなど) | 作者の好みが入っている。このサイトの基準とぶつかる規則がある | 試した。8 ページ × 2 幅 |
| Nielsen の 10 のヒューリスティクス | 使いやすさの観点(今どこにいるか分かるか、一貫しているか、など) | 人(または Claude)の評価 | 画面写真の見直しで観点として使った |
| unslop、Vercel の web-interface-guidelines | 磨き方の点検表 | 点は出ない | 観点として使った |
| Impeccable の `critique`・`audit`(LLM が評価) | 総評 | 評価する側の好みに寄る | 試していない |

確認:

- 計算後のスタイルを数える調べは、決めたルールの見張りとしてよく働いた。「11px 未満の文字がどのページのどの部品にいくつ」まで出る。
- 楽曲記事は記事ごとに独自のデザインにする決まりなので、記事の中のグラデーションや光は違反に数えない。数えるのは共通の枠(ヘッダー、下部タブ、一覧)だけにする必要がある。
- Impeccable の `kicker-above-heading`(見出しの上の小さいラベル)は、このサイトが基準にしている読みものの見た目そのもの。**道具の規則よりサイトの基準を優先**し、ぶつかる規則は外す。`low-contrast` は 2-2 と同じ白い背景の誤検出。
- 数え上げだけでは出なかった問題が、画面写真で見つかった(下部タブの現在地が違う。plan/77 の 4-3)。数え上げと目で見るのは両方要る。

### 2-4. コンテンツ

| 方法 | 分かること | 限界 | 試したか |
|------|-----------|------|---------|
| **ビルド済み HTML の総なめ**(cheerio) | title・description・canonical・hreflang・OGP・構造化データの欠けと重なり、h1 の数、noindex とサイトマップの食い違い、本文の短いページ、切れた内部リンク、寸法の無い画像 | 中身の良し悪しは分からない | 試した。3,680 ファイル全部 |
| 外部リンクの生死(linkinator 8.1.0、または自前) | 切れた出典 | 機械のアクセスを断るサイトは判定できない | 試した。読みものの 110 件 |
| **Google の「役に立つ、信頼できる、人のためのコンテンツ」の自己点検** | 独自性、だれが・どうやって・なぜ書いたかが示されているか、など | 質問に答える形。人(または Claude)の判断 | 構造で分かる所だけ当てた |
| 記事の原稿の数え上げ(文字数、出典の数、日付) | 記事ごとの厚み、出典の付き方 | 厚み ≠ 質 | 試した。69 本 |
| textlint(16.1.0) | 表記のゆれ、長すぎる文など | 技術文書向けの規則集はエッセイの声に合わない | 試していない |

参考(出典 17):

- Google の自己点検は、内容と質(11 問)、専門性(4 問)、人のための内容か(5 問)、検索のためだけの内容の兆し(11 項目)、「だれが・どうやって・なぜ」の 3 点から成る。点数ではなく問い。

確認:

- 総なめはブラウザを使わないので軽く、サイト全体(3,680 ファイル)を漏れなく見られる。切れた内部リンクとサイトマップの食い違いはこれで見つかった。
- 外部リンクは、歌詞サイトなど 13 件が機械のアクセスに 403 を返した。**403 は「切れている」ではない**。別枠(人が見る)にする。YouTube は Node の `fetch` が失敗するので、oEmbed を curl でたたいて確かめる。
- 記事の中身の評価は、書き直しや解釈の強化につながりやすい。スキルは **評価だけ** にとどめ、原稿に手を入れない(記事の声と執筆方針を守る)。

## 3. 試して分かった落とし穴(スキルに書き込むこと)

1. 背景が透明なので、コントラストの検査は本当の背景色を入れてからやる。独自の背景を持つページは別扱い。
2. 速さは本番で、3 回以上の中央値。ほかの重い処理と同時に走らせない。
3. Lighthouse の CLS は読み込み直後のずれも数える。自前の計測でも捨てずに両方出す。
4. 楽曲記事の独自デザインは、共通のデザインのルールで裁かない。
5. Impeccable の規則のうち、サイトの基準とぶつかるもの(`kicker-above-heading`、`hero-eyebrow-chip`)は外す。
6. 外部リンクの 403 は「判定できない」。切れたとは書かない。
7. 画面写真や結果のうち、利用者のアカウント名が写る画面(診断のタイプ詳細、ツアーナビ)は、報告に貼らない。
8. この PC は重い処理を 1 つずつ(メモリ不足で落ちたことがある)。ビルド、配信、ブラウザの計測を重ねない。
9. 機械で 0 件でも「適合」「問題なし」とは書かない。測っていないもの(実機、読み上げ、フィールドデータ)を毎回書く。

## 4. このサイトで勧める組み合わせ

| 領域 | 機械で測る | 見て判断する | 人に残す |
|------|-----------|-------------|---------|
| パフォーマンス | Lighthouse(本番・決めた 12 ページ・スマホ 3 回の中央値と PC 1 回)、ずれの出どころの自前計測 | LCP の要素、重いファイル、ずれの原因 | フィールドデータ(鍵か GA4 の接続が要る)、実機 |
| アクセシビリティ | axe-core(38 ページ × 2 幅 × 2 テーマ、本当の背景で)、キーボードで歩く、押せる物の大きさなど自前の調べ | 「要確認」の中身、独自デザインの扱い | 読み上げ、iPhone、拡大表示 |
| デザイン | 計算後のスタイルの数え上げ、画面写真 | サイトの基準(plan/71 ほか)と Nielsen の観点で写真を見る。Impeccable は参考 | 好みの最終判断 |
| コンテンツ | ビルド済み HTML の総なめ、内部リンク、外部リンク、記事の数え上げ | Google の自己点検の問いに照らす(評価だけ) | 403 の出典、記事の中身の判断 |

入れないと決めたもの: Unlighthouse(全ページは重い)、Lighthouse CI(今は 1 人で回すので予算の自動判定までは不要)、textlint の技術文書向け規則(エッセイの声に合わない)。

## 5. スキルにする時の案

置き場所は `.claude/skills/<名前>/SKILL.md` と、同じ場所の `scripts/`(今回書いた測定スクリプトを整えて入れる)。作り方の決まりは出典 18。リポジトリには `.claude/skills/batch-review/` が先にある。

- **引数で範囲を選ぶ**: `perf` / `a11y` / `design` / `content` / `all`。全部やると長い(見積もりで 30〜40 分)ので、普段は 1 つずつ。
- **流れ**: (1) 8000・9000 番が空いているか見る → (2) 速さは本番に当てる → (3) それ以外は、今の `public/` が新しければそのまま配って測る(古ければビルドするか聞く) → (4) 結果を前回と比べる → (5) `plan/` に報告を書く。
- **出すもの**: 領域ごとの数字、前回からの増減、見つかったことの一覧(確認・要確認・未確認の区別と、直す場所)、測っていないもの。
- **しないこと**: 見つけた問題をその場で直さない。デプロイしない。記事の原稿を書き換えない。GA・Search Console・シートに書き込まない。
- **前回との比べ**: 数字を JSON で残して差を出す。置き場所は決めていない(リポジトリに入れると差分が増える。入れないと PC を替えた時に消える)。
- **道具の入れ方**: Lighthouse・axe-core などは今は一時フォルダに入れている。`devDependencies` に足すか、`npx` で都度取るかは決めていない。

## 6. まだ確かめていないこと

- 実際の利用者の数字(CrUX・GA4)が取れるか。PSI の API の鍵は認証情報なので、用意するかどうかはユーザーが決めること。
- textlint をこのサイトの文体に合わせて使えるか。
- Impeccable の `critique`(LLM の総評)が役に立つか。
- Safari(WebKit)での axe の結果。今回は Chromium だけ。
- スキルを別のモデル・別の effort で回した時に、見て判断する部分がどのくらい揃うか。
